# 复感智联 · 智能评估系统

面向柔性多模态传感器的智能评估系统前端。配套项目为「复感智联」——基于仿鱼鳞仿生结构与 MWCNTs/GR/VO₂/SR 多元纳米复合材料的柔性应变-温度双模式传感器，本系统负责传感器数据的采集展示、康复运动识别结果呈现与评估报告生成。

### 两个必须知道的注意点

**① `src/components.d.ts` 要提交进仓库。** 它是插件生成的类型声明，让 `vue-tsc` 认识那些"凭空出现"的组件。`npm run build` 先跑 `vue-tsc` 再跑 `vite`，不提交的话 CI 上类型检查会失败。**新增组件后需要先跑一次 `npx vite build` 重新生成**，否则类型检查会报找不到组件。

> ⚠️ **这个生成器不太稳，跑完 dev / build 后它经常变脏，有三种形态**（2026-09-22 观察）：
>
> 1. **行尾被重写**（最常见）—— `git diff` 看不出差异，`git status` 却报 M。
>    用 `git diff --ignore-cr-at-eol` 才能确认没实质变化。
> 2. **生成结果不确定** —— 同一个代码状态，一次生成带 `ElSwitch`、另一次不带，
>    而 `ElSwitch` 在整个 `src/` 里没有任何地方使用。
> 3. **文件被写坏** —— 出现过一次：文件已经正常收尾，后面又接了一段残缺片段，
>    于是 `vue-tsc` 报一堆 `TS1005 Unexpected keyword`。
>
> **看到它变脏，直接 `git checkout -- src/components.d.ts` 即可**，不用去查代码
> 改了什么。做 git 操作（rebase / merge）前必须先清掉它，否则会报
> "cannot rebase: You have unstaged changes"。
> 如果是形态 3，**重跑一次 `npm run dev`** 让它重写就行 —— 不要怀疑自己的代码。
>
> 治本是把该文件加进 `.gitignore` 并 `git rm --cached`（**尚未执行**）。

**② 中文语言包改由 `<el-config-provider>` 提供。** 原先是在 `main.ts` 里 `app.use(ElementPlus, { locale: zhCn })`，按需引入后插件不再全局安装，改在 `App.vue` 里包一层。不改的话分页器、日期选择器、确认框的内置文案会退回英文。

> 顺带一提：改成按需引入后类型检查变严了，`el-table` 插槽的 `row` 从 `any` 变成了 `DefaultRow`，暴露出 `Devices.vue` 里三处未经验证的类型断言。这是好事，已用 `asDevice()` 显式收窄。

### 关于 404.html

GitHub Pages 是静态托管，**不支持 SPA 回退**：直接访问 `/fugan-zhilian/analysis` 或在深链接上刷新，会因为找不到同名文件而返回 404。

**部署流程**里加了一步把 `index.html` 复制成 `404.html`（在
`.github/workflows/deploy.yml` 里，**不在 `npm run build` 里**）。Pages 遇到未知路径时
会用这个页面兜底，应用照常启动，vue-router 按 `location.pathname` 解析出正确路由。

> ⚠️ 别在本地找 `dist/404.html` —— `npm run build` 只跑 `vue-tsc && vite build`，

### 自检脚本本身也会出错

写这些断言时踩过**四次**「断言错了而不是代码错了」，都值得记下来：

1. **用四舍五入后的值比唯一性**：直腿抬高和靠墙静蹲设计上都是小 ROM，随机波动下会撞到同一个整数
2. **上界卡在设计值上**：屈膝滑动设计范围 5–100°，叠加 ±6% 会话波动后最大到 100.6°，卡 100 会偶发误报
3. **概率算错量级**：信号丢失的概率是对**每个采样点**生效的，不是对"每次丢失事件"——少乘了一个量级，导致断言阈值定低了 16 倍
4. **睡固定时长等异步跳转**：`waitForTimeout(3000)` 在 Supabase 响应慢时不够，
   三次里失败一次 —— 而每次跑的代码完全一样。这类断言最坑：它看起来像代码
   回归，会让人去翻根本不存在的 bug。改成 `waitForFunction` 等真实状态。

第一条跑 8 次才复现 1 次，第三条跑 20 次失败 11 次。**如果只跑一遍就交付，这些 flaky 断言会在某次演示前突然变红。** 自检脚本改完要连跑 20–30 次确认稳定。

### 信号模拟器

实时监测页的数据由 `src/lib/simulator.ts` 生成（硬件尚未接入）。模拟器不是随机数发生器——它按传感器实际参数复现信号链路：

```
关节角度 ──映射──> 伸长率 ──GF──> 应变分量 ┐
                                          ├─> 原始信号（两者耦合）
局部温度 ────────────TCR──────> 温度分量 ┘
```

自检脚本验证这些物理关系确实成立，比如 `原始 = 应变 + 温度` 的残差仅为噪声、温度分量与温度呈完全负相关、肌电在向心收缩期强于离心期。改模拟器的常数后跑一下，能立刻发现有没有把关系改坏。

### 热敷预警的阈值：一次「一直亮着的告警」

这是 2026-09-22 改的一处，起因是拿系统的参数去核对计划书。

**发现的问题**：模拟器里热敷袋的目标温度是 **50°C**，而预警阈值是 **45°C**。
两者反了 —— 实测一次 20 分钟的热敷会话：

```
阈值 45°C 首次触发于     19.3 秒
超过阈值的时长           19.7 分钟 / 共 20 分钟   ← 98.5% 的时间都在报警
```

**98.5% 的时间都亮着的安全告警不携带任何信息**，等于没有告警。而计划书把
「独居老人热敷预警」当作核心场景。

**根因是计划书自己有个内部矛盾**（两处原文）：

> 治疗温度通常为 **40-50℃**，单次时长 15-20 分钟
>
> 临床研究表明，皮肤接触 44℃ 热源持续 6 小时、或接触 **50℃ 仅需 5 分钟**，
> 即可造成不可逆的低温烫伤

50°C 既是"治疗温度的上限"，又是"5 分钟即不可逆损伤"。所以光调一个数消不掉矛盾
—— 必须把**阈值**和**模拟的正常目标**一起定。

**改法**：

| | 改前 | 改后 | 依据 |
|---|---|---|---|
| 预警阈值 | 45°C | **50°C** | 计划书点名的危险温度 |
| 正常热敷目标 | 50°C | **45°C** | 计划书治疗区间 40-50 的中部 |
| 过热档 | 无 | **55°C**（偶发） | 见下 |

这样正常热敷**永远不报警**（实测 20 秒内峰值 42.6°C），只有真的越界才报。

**为什么必须补一个"过热档"**：目标降到 45 之后预警就再也没机会出现了，
而它是产品的核心场景。所以加了一种真的会越界的会话 —— 形态选**「加热过久」**
（袋温冲到 55°C）而不是"忘记取出"：后者是**时间**维度的问题（计划书：接触
44℃ 持续 6 小时也有害），温度通道测不出时间；加热过久则是实打实的温度越界。

**这里有一个刻意的演示编排，要说明白**：纯按概率算，首次过热平均要等 5 分半
（实测有个种子等到了 23 分钟），演示时干等着看不到。所以**进入热敷场景后第一段
过热保证在 25~55 秒内出现**，之后才回到随机频率（约每 5 分钟一次、每次 1~2 分钟，
也就是两成左右的时间处于告警状态）。答辩被问"多久过热一次"时，要按后一个频率回答，
**不要把开场那一段当成真实发生率**。

**顺带修掉的两处**：

1. 温度图的纵轴上界原先是 **52**，而过热档会冲到 55 —— **超出的那段被直接裁掉，
   预警事件在图上反而看不见**，只剩状态栏一个标签在闪。改成让色带和坐标轴共用
   一个常量 `TEMP_AXIS_MAX = 58`；分成两个数写迟早会漂，漂的后果就是这个。
2. 演示数据里那条预警原本是 `warning / 45.8 / 阈值 45`，三个数在新阈值下全都不
   成立。改成 `critical / 52.8` —— 跟着实时监测的口径走（温度越阈在 useMonitor
   里就是 critical）。**代价是首页演示分数从 90 掉到 78**：想过保持 warning 以
   保住分数，但那会造出"预警记录页显示黄灯、实时监测页对同一件事显示红灯"的
   矛盾，比分数不好看严重。

**断言也跟着升级了**（19 → 21 项）：原来那条「温度跨越 45°C 预警阈值」在正常
会话里恒真，现在拆成三条更强的：

```
正常热敷从 40°C 起步、始终不越过预警阈值
过热事件会跨越 50°C 预警阈值
而且第一次越界不是一开始就发生（正常热敷阶段是干净的）
```

⚠️ 改这个的时候还发现 `check-simulator.ts` 的 `run()` 一直用 `Math.random`
—— 加了随机过热之后，断言会随运行漂移。已改成固定种子（`lib/rng.ts` 的 `makeRng`）。
这是顺带修好的一处旧隐患：项目早先就因为 flaky 断言吃过亏（见上面「自检脚本本身
也会出错」），而模拟器这一组一直在漏。

### 肌电-运动学融合分析

命题答题要求点名了三项分析能力，第三项是「结合肌肉骨骼模型的运动学数据融合（如关节角度与肌电信号的关联性分析）」。实现在 `buildEmgAnglePhase()`。

**为什么不能只算一个相关系数**：一次屈伸动作里角度先升后降、肌电也先强后弱，两者都是非单调的，直接算 Pearson 相关系数会接近 0。有意义的是**分相位看**——把每个角度上的肌电按向心期（角度增大）和离心期（角度减小）分成两条曲线，画在同一张图上会形成一个闭合环路，两臂的高低差就是发力相位是否正确的直接证据。**肌电峰值若落在离心期，说明存在代偿。**

**一个踩过的坑**：峰值角度原本取"RMS 最高的那一箱"，实测**无偏但标准差高达 12°**——同一患者同一动作，连续两次评估可能显示"峰值 30°"和"峰值 75°"，治疗师会认为系统坏了。根因是肌电包络本身很宽（相位标准差 0.12 折合约 11°），加上每箱只有约 2 个采样点，argmax 极易被单箱噪声带偏。改用**强势区（≥80% 峰值）的加权质心**后标准差降到 5.4°。试过加大分箱宽度，没有帮助——剩下的波动由包络宽度决定。

**静力动作会被排除**：靠墙静蹲的角度只在十几度内微调，没有明确的向心/离心交替，硬做会得到两条几乎重合的曲线和一个没意义的比值。此时返回 `applicable: false` 并说明原因，而不是硬画一张图。

### 评估结论

把技术指标变成**有名字的功能结论**。原来那块叫「评估建议」，它已经在做类似的事，
但把依据和建议揉在一句话里、用的是另一套语气分级、覆盖的类型也少。

现在的输出刻意是三个独立字段：

```
label      结论。家属能读 —— 一句话说清这次做得怎么样
evidence   依据。医生能核 —— 具体到数值，一行灰字
action     该做什么。给训练动作，不给治疗方案
```

「结论要简单，依据要完整」—— 和恢复评分是同一条原则。

#### ⚠️ 合规边界（改文案之前先读这段）

这个产品**不是医疗器械**，没有 NMPA 注册。所以措辞有一条硬线：

| ✗ 不能做 | ✓ 可以做的 |
|---|---|
| 给疾病名称「膝关节僵硬症」 | 描述**测量结果**「活动度 62°，低于康复目标 90°」 |
| 说「诊断为…」 | 描述**功能状态**「本次屈曲幅度不足」 |
| 给治疗方案：药物、剂量、手术 | 给**训练建议**「在无痛范围内逐步增加幅度」 |
| 声称可替代医生判断 | 报**安全风险**「皮温接近阈值」 |

**一条可操作的判据：结论的主语必须是「数据」或「训练」，不能是「患者」。**

```
✗  你的膝关节僵硬了              ← 对患者下判断
✓  本次膝关节屈曲活动度低于目标    ← 对测量结果下判断
```

界面上这一块的标题用「评估结论」而不是「诊断结果」——名字本身就在划界。
面板底部常驻一句免责声明（文案在 `findings.ts` 顶部）。

**这条边界有断言守着**：自检会把所有结论类型跑一遍，检查有没有出现
「诊断 / 症 / 炎 / 处方 / 用药」这类词，以及结论的主语是不是患者本人。
文案随时会被改，靠人记住这条线迟早会忘。

#### 结论清单

| 结论 | 触发条件 |
|---|---|
| 活动度 / 保持角度达标、未达标 | 与**该动作自己的**目标比（完成度低于 70% 判红） |
| 肌电峰值落在离心期，发力时机偏晚 | 向心/离心比值 < 0.9 |
| 各轮次动作幅度差异较大 | 轮次间变异系数 > 0.15 |
| 后半程肌电强度明显下降 | 后半程较前半程降 > 25% |
| 识别出的动作与实际所选不一致 | `recognized ≠ performed` |
| 动作识别置信度偏低 | 置信度 < 0.7 |
| 局部皮温超过安全阈值 | `tempMax ≥ 50`（计划书点名的危险温度） |
| 本次较以往同动作有进步 / 有所回落 / 持平 | 同动作历史 ≥ 3 条，且变化 > 12% |

**全部从已有的量派生，不需要新采集。**

#### 两个刻意的设计

**① 一次最多展示 3 条，其余折起来。** 一次评估冒出五条并列的结论，等于一条都没说
—— 用户会全部略过。排序先按红黄绿、再按优先级，温度安全永远排第一。

**② 与历史对比只比同动作。** 直腿抬高的活动度只有 10° 上下、屈膝滑动接近 100°，
跨动作平均出来的数不代表任何一个动作。而且静力动作要比**保持角度**而不是活动范围
—— 拿后者去比会得出完全相反的结论。

「有所回落」而不是「退步了」：单次波动很常见，说成退步会引起不必要的焦虑。

### 数据分析页的结论

首页有本周评分，评估页有单次结论，而**数据分析页原先从「六个数字」直接跳到
「四张图」，中间一句人话都没有** —— 用户得自己把曲线翻译成"在进步还是停滞"。
而导出 PDF 走 `window.print()`，所以拿出去的报告也是四张图加六个数，
没人看得出说明什么。

#### 三层结论的分工

这是最容易做错的地方：**再算一个分数就是首页的复读，搬最后一次会话的结论过来
就是评估页的复读。** 三层的分工写死在 `src/lib/trend.ts` 的开头：

| 层 | 回答的问题 | 窗口 |
|---|---|---|
| 首页 `insight` | **本周**恢复得怎么样 | 固定 7 天 + 14 天基线，加权成一个分数 |
| 评估页 `findings` | **这一次**训练做得怎么样 | 单次会话 |
| 分析页 `trend` | 所选窗口内，**每个动作分别**往哪个方向走 | 用户自选（7 / 30 / 90 天或全部） |

所以 `trend.ts` **刻意不算分数、不评价单次**。它独有的价值是另外两页都给不出的：

```
首页只能给：  本周 88 分，恢复良好
这里能给的：  屈膝滑动 30 天从 78° 升到 93°，已达目标
              直腿抬高一直在 10° 附近，30 天没有变化
              坐位伸膝差目标 8°，是唯一还没达标的动作
```

#### 四个判断

**方向用「前后半段均值」比。** 不用首尾两点 —— 两端各一次异常值就足以把结论
翻过来；也不用最小二乘斜率 —— "每周上升 2.3°"家属读不出，而且它同样怕异常值。
前后半段均值是**同一批真实数据**的平均，方向和图上的数字天然一致，不会出现
"显示 78° → 76°、却说在上升"这种自相矛盾。（`findings` 判断疲劳趋势用的是
同一个办法，口径一致。）

**门槛按目标的比例算，不是绝对度数。** 直腿抬高目标只有 10°、屈膝滑动 90°，
用一个绝对阈值两头都错。取 `max(2°, 目标 × 8%)`。所以同样涨 2.5°，对直腿抬高
算进步、对屈膝滑动算持平 —— 断言里专门钉了这两个反向用例。

**达标看最近一次，不看历史平均。** 前四次都 70°、最后一次 92°，问的是"现在
能不能达标"。而这件事**一次训练就能回答**，所以它不需要趋势（见下）。

**覆盖率的分母是"从首次记录到今天"，不是窗口长度。** 一个三天前才开始训练、
每天都练的患者覆盖率是 100%，不该被说成"练得太少"。

**静力动作走保持角度。** 这是同一个坑的**第五处**（前四处见上面「达标判定」一节）。
反向断言专门构造了"活动范围一路上涨、保持角度没动"的数据，必须判持平 ——
**正向测试只能证明"能出结论"，只有反向测试能证明实现真的在用 `hold_deg`。**

#### 方向判不出来时，达标状态照样给

"在往哪个方向走"和"现在达没达标"是**两件事**：

```
方向  需要 ≥ 4 天，两三个点连不出趋势
达标  一次训练就能回答
```

原先天数不够时整条丢掉，于是刚练了三天的患者、或者选了「近 7 天」的用户，
界面上**一个动作都不显示** —— 连"哪个达标了"都看不到。现在 `TrendItem.trend`
可空：方向答不了就明说"看不出方向"，达标该给照给。

实测演示数据切到「近 7 天」：

```
改之前   逐动作 0 行、结论 0 条 —— 整个结论区只剩一句"看不出趋势"
改之后   逐动作 4 行，每行给出「看不出方向 / 最近 95.3° / 目标 90° / 2 天记录」
```

**门槛没有降。** 3 个点判方向是不稳的，降到 3 是拿噪声编结论 —— 问题不在门槛，
在于把"看不出方向"和"看不出达标"一起丢掉了。

⚠️ 还有一条最容易写错的：**"看不出来"和"没变化"是两回事。** 记录不足且未达标时，
可以报"记录还太少、看不出变化、且未达标"（那是事实），但**不能**报"没有明显
变化"（那是编了一个我们并不知道的结论）。两条结论分开，键也不同
（`trend_insufficient` / `trend_stuck`），断言里正反两个方向都钉了。

#### 短窗口会给提示

7 天最多 7 个数据点，而一天只练一个动作的话，每个动作还分不到 4 天 ——
算出来的方向主要是噪声。窗口短于 14 天时页面上给一条提示，引导改用 30 天以上。

#### 演示数据回退

分析页原先对没有记录的访客只显示一句"所选范围内还没有训练记录" ——
四张图和结论区**一个都不出现**。而首次打开链接的人（评审、家属、队友）
一定没有历史。现在和首页一样回退到演示数据，并挂「演示数据」声明条
（两页共用 `components/DemoNotice.vue`，避免措辞漂开）。

⚠️ 判据是"**这个患者从来没有过记录**"，不是"当前窗口内没有记录" ——
后者会让一个真实用户选了「近 7 天」而恰好那周没练时，看到一组别人的数据。

⚠️ 演示记录**必须自己按窗口筛一遍**。真实数据是 `fetch({ from })` 带回来的，
时间范围在请求里就过滤了；演示数据是内存里造的，没经过那道。**漏了这一步
的话「近 7 天」还会显示 21 天的记录** —— 而这一页的结论**全都带窗口**
（"近 7 天共…"），标签一假，整段结论都在描述一个不是用户所选的范围。
（第一版就漏了，实测才发现。）

### 康复评估的达标判定

不同动作的达标指标**不是同一个量**，混用会得出错误结论：

| 动作类型 | 判定指标 | 例 |
|---|---|---|
| 动态屈伸（坐位伸膝、屈膝滑动、直腿抬高） | **关节活动范围**（行程） | 坐位伸膝要求达到 80° |
| 静力维持（靠墙静蹲） | **保持角度** | 靠墙静蹲要求保持在 55° |

靠墙静蹲是静力动作，活动范围本来就很小（只有姿势微调）。**拿它的活动范围去比 55° 的目标会得出「远未达标」的错误结论**——实际要看的是它保持在了多大角度。这两者在 `src/lib/assessment.ts` 里由 `AssessMetric` 区分，评估页会据此切换图表标签与目标线。

⚠️ 四个动作的名称与各自的达标值是按常见膝关节术后康复方案拟定的，计划书里只写了「四类典型膝关节康复运动」并未列出具体名称。**团队应按实际康复方案核定 `EXERCISE_PROFILE` 这张表。**

### 数据库核对脚本

两个脚本都在 Supabase SQL Editor 里执行，用途不同：

| 文件 | 用途 |
|---|---|
| `supabase/verify_migrations.sql` | **精简版**，13 项 / 74 行。只回答"迁移都应用了没"，适合快速粘贴 |
| `supabase/verify_summary.sql` | **完整版**，20 项 / 239 行。含策略、触发器、列级授权等明细，迁移后完整核对用 |
| `supabase/verify_rls.sql` | **明细版**，151 行。RLS 与权限逐段核对，**适合分段选中执行** |

> ⚠️ SQL Editor 只渲染**最后一条语句**的结果 —— 整段贴 `verify_rls.sql` 进去
> 只能看到第 7 段。要做一次性核对用 `verify_summary.sql`（它把关键检查合并成了
> 单条 SELECT）；`verify_rls.sql` 是分段看明细用的。
>
> `verify_summary.sql` 有 239 行，粘贴时也容易只选中一部分，导致
> `syntax error at end of input`。日常检查用精简版。

### 预警记录

实时监测页在温度超标、信号中断时会往 `alerts` 表写记录，家属端收到的提醒也来自这张表。

这个页面补的是一个**功能缺口**：在此之前预警是"只写不读"的——首页只有个数字红点，点不进去，也没有列表页，`acknowledge()` 从未被任何界面调用，所以**红点只增不减**。低温烫伤预警是产品的安全核心卖点，看不到内容等于没做。

### 访客模式

**打开网站直接进入「实时监测」，不需要注册。** 落地页选它是因为四路曲线由模拟器驱动、不依赖任何历史数据，访客一进来就能看到东西在动。

访客首次进入时**静默建立一个匿名账号**（Supabase Anonymous Sign-in），此后所有功能与正式用户完全一致。

**为什么要建账号而不是直接放行**：`anon` 角色在业务表上没有任何授权（迁移 2 刻意 revoke 的），直接放行会让每个数据页面拿到 `42501 permission denied`。匿名账号拿到的是正常的 `authenticated` 角色，**既有 RLS 原样生效**，所以页面和数据层没有为"访客"写任何分支。

**注册 = 升级当前账号**（`updateUser`，不是 `signUp`）：uid 不变，**访客期间绑定的设备、保存的训练记录全部保留**。这条承诺由 `supabase/dev/e2e_guest_mode.mjs` 实测验证。

**访客点「登录」会二次确认**：Supabase 的登录是替换会话，用已有账号登录后匿名账号的数据不会跟随。想保留数据必须走「保存账号」。

⚠️ 控制台需开启 **Anonymous Sign-ins**（Authentication → Sign In / Providers）。未开启时守卫退回登录页兜底。

**建访客会话失败时不能缓存失败结果。** `ensureGuestSession()` 原本写的是 `guestPromise ??= createGuestSession()`，而 `createGuestSession()` 出错时返回 `false` 而不是抛异常 —— 那个 `false` 被永久缓存，于是**一次网络抖动或频率限制之后，这个访客在整页刷新之前再也进不去了**：之后每次跳转都拿到同一份缓存，一路弹回登录页，而且不再重试。

失败时必须把 `guestPromise` 清掉。这条有专门的端到端用例（拦掉 `/auth/v1/signup` 模拟失败，再放开、在**同一个页面里**重试点一次）——反向验证过，改回旧写法该用例会失败。

### 找回密码

流程：登录页点「忘记密码」→ 填邮箱 → 收到邮件 → 点链接 → 设置新密码。

⚠️ **邮件回跳的是站点根目录，不是 `/reset-password`。** 看着绕，但必须如此：

GitHub Pages 是静态托管，`/fugan-zhilian/reset-password` 这种深链接没有对应文件，Pages 用 `404.html` 兜底 —— **HTTP 状态码是 404**。桌面浏览器照常渲染，但邮件客户端的内置浏览器（QQ 邮箱、163 邮箱那些）拿到 404 往往直接弹自己的错误页、不渲染内容。

而这时候**令牌已经被消费掉了**：邮件链接指向的是 Supabase 的 `/auth/v1/verify`，那一步就用掉了一次性令牌，之后才 302 到我们这儿。于是用户看到的是「在邮箱里打开报错，转到浏览器就显示失效」——**一次点击废掉一封邮件**。这个问题实际发生过。

指向根目录返回 200，谁都能渲染。路径本来就不重要：识别恢复流程靠的是 URL 里的 hash，落地之后路由守卫会把用户送到设置新密码页。

改密码成功后会自动 `signOut({ scope: 'others' })`，**把其它设备上的会话一并作废**。改密码通常是因为原密码可能已经泄露，不作废旧会话的话攻击者手里那个还能继续用，改了等于没改。当前这台不受影响。

⚠️ **必须先配 Redirect URLs，否则线上收不到邮件链接的效果。**

Supabase 控制台 → Authentication → URL Configuration → Redirect URLs 里加上：

```
http://localhost:5173/fugan-zhilian/**
http://localhost:4173/fugan-zhilian/**
https://alpha5954.github.io/fugan-zhilian/**
```

**配错的失败是无声的。** 实测过 GoTrue 对不在白名单里的 `redirectTo` **不报错**，而是静默丢弃、改用站点的 Site URL —— 接口返回成功，前端也没有任何异常，只有用户点的邮件链接会跳到一个陌生的地址。

（好在还有一层兜底：`authRedirect.ts` 认的是 URL 里的 hash，不管落在哪个路径上都能认出恢复链接并把人送去设置新密码页。所以只要**站点的 Site URL 本身指向本站**，即使白名单没配也能走通。但 Site URL 默认是 `http://localhost:3000`，用手机点邮件就废了——白名单还是要配。）

实现上还有一个必须知道的坑，它决定了这个功能能不能工作：

**① 不能靠 `PASSWORD_RECOVERY` 事件，要从 URL 里同步读。**

Supabase 的恢复链接把令牌放在 hash 里（`#access_token=...&type=recovery`），SDK 解析完会把它清空。而 SDK 发出 `PASSWORD_RECOVERY` 事件用的是**一句裸的 `setTimeout(..., 0)`**，不进 initialize 的通知队列；`getSession()` 之后我们还跟着一次 `fetchProfile` 网络请求——等那之后再订阅，事件早发完了。用户会被当成普通登录送进首页，密码根本没改，而他以为自己改过了。

所以 `lib/authRedirect.ts` 里对 URL 的解析放在**模块求值阶段**，而它必须是 `main.ts` 的**第一个 import**——排在 SDK 后面加载就读不到了。这条顺序约束在那个文件的开头写着，改的时候别挪。

**② 守卫要把用户"锁"在设置新密码页上。**

点完邮件那一刻，用户手里是一个货真价实的登录会话。没有这道锁的话他会一路正常地进首页、逛各个页面，然后大概率再也想不起来自己是来改密码的。锁在 `router/index.ts` 的最前面，公开页面也不放行。

三种进不到表单的情况分开说，而不是统一一句"出错了"：**链接过期**（URL 带 `error_code`）、**令牌没换成会话**（可能被邮件客户端截断）、**直接敲地址**。前两种给出「重新申请一封」，第三种指回登录页。

**④ 地址栏里的令牌要清掉——而且只能让 vue-router 去清。**

令牌和错误码用完必须从 URL 里抹掉：否则会随 `Referer` 头漏给第三方、被截图带走，用户刷新时还会拿同一个用过的令牌再解析一遍、报出一个和他无关的错误。

但**直接在 `authRedirect.ts` 里调 `history.replaceState` 是白费力气**。实测的调用记录：

```
1. /reset-password#error=...   ← vue-router 初始化，把带 hash 的地址记进 history.state
2. /reset-password            ← 直接 replaceState（清干净了）
3. /reset-password#error=...   ← vue-router 拿它自己那份记录又写了回来
```

vue-router 保存滚动位置时会用它内部记的地址做 `replaceState`，所以第 3 步必然发生。正确做法是在路由守卫里**返回一个去掉 hash 的重定向**，让 router 自己的记录一起变成不带 hash 的。判断"要不要清"由 `consumeAuthHashFlag()` 一次性给出（`isAuthCallback` 那条纯逻辑有自检覆盖）。

**③ 错误提示要翻译。**

Supabase 的认证错误是英文的（`Invalid login credentials`），中文界面里只有报错冒英文，用户读不懂也不知道下一步干什么。`lib/errors.ts` 的 `authErrorInfo()` 按错误码翻成中文，并把码一起返回——因为 `email_not_confirmed` 需要界面额外给一个「重新发送确认邮件」的按钮，光提示"去验证邮箱"没有用。

⚠️ 「如果该邮箱已注册，邮件已发出」——**措辞不能写成"邮件已发往 xxx"**。Supabase 对未注册的邮箱同样返回成功，这是刻意的反枚举设计，否则任何人都能拿这个接口试探哪些邮箱注册过。

## 结论层

> 结论层一共**三层**，本节只讲第一层（首页评分）。另两层在上面
> 「算法与结论层」里：**单次评估结论**（`findings.ts`）与
> **一段时间的方向**（`trend.ts`）。三层的分工见 `trend.ts` 开头的表格。

界面是给**懂技术的人**看的（波形、RMS、GF、TCR 全部直接显示），
但技术指标本身回答不了"恢复得怎么样"这个问题。结论层补的就是这一段。

它和「家属模式」不是一个东西 —— 那个模式已经撤掉了（见下），
结论层保留了下来，因为它对任何读者都有用：医生说"活动度 66°"，
结论层说"还差 14° 达标，本周是差距最大的动作"。

### 结论层：`src/lib/insight.ts`

改造前数据流是断的：

```
传感器 → 原始信号 → 技术指标(RMS/GF/TCR/ROM) ──✂── 直接甩给用户
```

家属看到 `GF=2.4`，这对他没有任何意义。补上的是中间那段：

```
传感器 → 原始信号 → 技术指标 → 【结论层】→ 家属语言
                                   ↑
                              个人基线
```

**恢复评分由四个可解释的分量加权**，不是拍脑袋给一个数：

| 分量 | 权重 | 怎么算 |
|---|---|---|
| 动作达标 | 40% | 本次完成值 ÷ 该动作的康复目标 |
| 进步情况 | 30% | 本周 vs 之前 14 天基线 |
| 动作稳定 | 15% | 本周完成度的变异系数 |
| 训练坚持 | 15% | 本周训练天数 ÷ 建议天数 |

**每一项都能在界面上展开看到依据**（「查看详细数据」里）。答辩时评委问"为什么是 88 分"，能一项一项翻给他看，而不是答"模型算的"。

#### 加权之后还要过两道调整

分数不是直接加权出来的，之后还有两步。**两步都必须写在界面上** —— 悄悄改分是这个界面最不能做的事，家属会觉得"我没做错什么，分数怎么掉了"。

**① 数据充分度收缩。** 样本少时把分数拉向中性值（65 分），避免"本周只练了 1 次"也算出一个看起来很确切的分数。

> 实测过不做收缩的行为：1 次做满 85 分、1 次不达标 30 分 —— **1 个样本给出了 55 分的区分度**。那不是在描述患者，是在描述随机性。加上收缩后同样的两例是 65 / 60，区分度压到 5 分。

**② 安全下调。** 安全事件用**乘数**而不是扣分项：

| 最严重的预警 | 系数 | 对满分一周的实际影响 |
|---|---|---|
| critical（温度越阈值、信号中断） | ×0.80 | 100 → 80 |
| warning（接近阈值、识别异常） | ×0.92 | 100 → 92 |

> 2026-09-22 从 ×0.6 / ×0.85 调上来的。原先 40% 太重 —— 一周练满、
> 动作全达标、进步明显（原始分 100），一次严重事件直接掉到 60 分，
> 等于把一周的努力抹平。而且**乘数是按比例扣的，对本来就没做好的周
> 惩罚更重**（65 分的一周 ×0.6 = 39），做得差的人被罚两次。
>
> ⚠️ 代价是「严重事件必然把分数压进红灯」这个性质**没有了** —— 乘数做不到，
> 原始分高的时候扣完还是高（100 × 0.80 = 80，黄灯档）。真要那条性质得换成
> **封顶**机制（严重事件 → 本周评分最高 59 分），那是换算法不是调参数。
> 见 `SAFETY_PENALTY` 的注释。

> 旧版是**只变色不扣分**：有严重温度预警的一周仍然显示 85 分，只是把颜色变红了 —— 数字和颜色互相矛盾，而数字的说服力更强。医疗产品里不能这样。
>
> 用乘数是因为安全事件的影响**不该是线性的**：一次低温烫伤风险，不会因为患者本周动作达标率高就不算数。加分制里它可以被别的项抵消掉。
>
> 按**最严重的**那一条算，不累加 —— 3 次一般提醒不等于比 1 次严重 3 倍。次数写在文案里，不藏。

#### 分档负责解释分数

```
90–100  恢复优秀 · 与之前相比有明显进步
80–89   恢复良好 · 保持得很好，按当前方案继续
60–79   稳步恢复 · 进展平稳，继续按方案训练
40–59   需要关注 · 建议复查训练动作是否到位
 0–39   需要处理 · 建议联系康复治疗师
```

一个"完美但处在平台期"的患者会拿到 85 分，单看数字家属会问"为什么不是 100"。配上「恢复良好 · 保持得很好」就不用解释了。

⚠️ **分档的分界值必须与颜色分界（80 / 60）对齐。** 两边漂了会出现"同一个标签配两种颜色" —— 实测踩过：51 分和 61 分都显示「需要关注」，一个红一个黄。

#### 参数全部集中在 `src/lib/scoreConfig.ts`

权重、阈值、系数、分档、免责声明都在那一个文件里，算法实现里不再出现裸常数。每条都标了 `[待核定]` 或来源。

**这是给团队里懂康复的人用的** —— 他们可以直接改那些数，不用读算法实现。答辩时评委问"权重怎么定的"，翻这个文件比答"我们讨论定的"强。

⚠️ 里面有一条明确写了：进步度的 ±20% 映射**没有依据**，临床上更严谨的做法是用**最小可检测变化（MDC）**，膝关节活动度的 MDC 换算成相对值约 6%~11%，比 20% 小。**这一项值得让康复科重新定。**

#### 静力动作已接上（迁移 9）

在此之前，`rehab_sessions` 只有 `rom_deg`（活动范围），而靠墙静蹲的目标 55° 指的是**保持角度**。静蹲的活动范围天然只有 5~10°，拿它比 55° 会把做得完全正确的患者判成 0 分。

所以旧版注释里写着"根治的办法是给表加一列 `hold_deg`"，但一直没做 —— 代价是**这类动作在评分和达标统计里完全不存在**：一个只做静蹲的患者，"动作达标"那一项永远是 0 分。

迁移 9 补上了这一列，`insight.ts` 与 `analysis.ts` 都改成按动作类型取指标。老记录没有这个值且无法还原，代码按"跳过"处理，**不拿 rom_deg 去硬凑** —— 宁可少算，也不要算错。

#### 免责声明不是可选项

界面上必须带这句话：

> 本评分由系统根据关节活动度、训练依从性与传感器数据综合计算，属于康复过程中的趋势参考，**不是临床评定量表**。

KOOS、Lysholm 那类是经过信效度检验的**患者自评量表**，有常模、有验证。我们这个是**从传感器数据算出来的过程性指标**，两者不能混为一谈。答辩时被问"这个分数验证过没有"，诚实的回答是"没有" —— 界面上先写清楚反而是加分项，说成"类 KOOS 评分"会被当场问穿。

### 分数与风险：两个轴，而且**不可能**一致

这里走过一段弯路，而且**第二版也是错的**，值得完整记下来。

**第一版**：风险等级的颜色被用到了评分数字上，于是出现"92 分被涂成橙色需要注意"
这种自相矛盾的画面。当时的修法是拆开 —— `scoreBand` 管分数颜色，`band` 管
风险角标。

**第二版（错的）**：后来以为可以把两个轴"合并成一个"—— 让安全事件直接扣分，
分数本身就包含安全，于是 `scoreBand` 和 `band` 都从调整后的分数推出，声称
**必然一致**，还写了一条 `ins.scoreBand === ins.band` 的断言钉住它。

**那条断言是错的，而且这条性质在数学上就不可能成立。** 原因在 `bandFor()`
里有一条独立的预警分支：

```ts
if (hasCritical || score < 60) return 'red'
if (hasWarning  || score < 80) return 'yellow'
```

`band` 只要周内有严重预警就报红，**和分数无关**；而 `scoreBand` 只看分数。
乘数是按比例扣的，原始分越高扣完剩得越多 —— 100 分的周 ×0.80 还剩 80 分，
`scoreBand` 是绿、`band` 是红，必然打架。（原先的 ×0.60 也不行：
100 × 0.60 = 60，正好压在下边界上，浮点数一偏就翻。）

它一直绿，只是因为那条断言喂进去的数据原始分是 85，**碰巧绕开了边界**。
把测试数据换成满分的一周，它立刻红。

**现在**：承认两者是**不同的轴** —— 而且这本来就是对的。分数说的是"恢复得
怎么样"，风险说的是"有没有危险"；一个患者可以恢复得很好（92 分）但有一次
温度超标需要留意。界面上数字用 `scoreBand` 上色、风险由各张卡片自己的 `band`
表达，分开渲染。

> 顺带一个事实：`insight.band` **界面根本没有用到**，只有断言脚本在读它。
> 界面上所有风险颜色都来自各张卡片自己的 `band`。

那条断言换成了钉住**当初真正出问题的现象**：高分不能被风险染成橙/红
（实测截图发现过 92 分被涂成橙色）。测试数据也从原始分 85 换到 100，
把高端覆盖上 —— 那条假断言正是从这个缺口漏过去的。

### 图表视觉语言与数字排版

「高级感科技感」有两个版本：廉价版是霓虹暗底加发光边框，高级版是**精度**。这个项目走后者 —— 命题是传感器，评委要看的是"这家做的仪器很精密"，霓虹灯传达的是"这家做的是演示动画"。

#### 图表统一到 `src/lib/chartTheme.ts`

改造前四张图各写各的 option，同样是坐标轴，字号、颜色、网格样式都不完全一样 —— 单看每张都没问题，**摆在一起就"散"**。而"散"正是廉价感的来源。

| | 改造前 | 改造后 |
|---|---|---|
| 网格线 | 实线，铺满 | **虚线**，每轴 4 条 |
| 轴标签 | ECharts 的 `auto`，一屏二十几个刻度 | 按数量抽稀，最多 8 个 |
| 数值轴范围 | 固定或默认从 0 起 | `scale` 贴合数据 |
| 提示框 | ECharts 默认白框 | 项目样式：细描边、小圆角、浅阴影 |

**温度图是唯一的例外，必须固定范围。** 试过自适应 —— 皮温就在 33 上下，曲线确实占满绘图区好看得多，**但预警线直接跑到屏幕外**。温度是安全参数，患者要看的不是"我在 33.02 和 33.10 之间波动"，而是"我离烫伤还有多远"。固定范围留下的空白用一道**危险区色带**填成信息：曲线在色带下方 = 安全。

⚠️ 上界和色带取同一个常量 `TEMP_AXIS_MAX`（58）。原先色带画到 45–52、轴也卡在 52，而热敷的**过热档会冲到 55** —— 超出的那段被直接裁掉，**预警事件在图上反而看不见**，只剩状态栏一个标签在闪。分成两个数写迟早会漂，漂的后果就是这个。

#### 分类色从数据层移到视图层

`analysis.ts` 里原本写着 `['#409eff', '#67c23a', '#e6a23c', '#f56c6c']` —— **那是 Element Plus 的默认调色板**，和整套克制的品牌色不是一家的。

但数据层是纯函数、运行时没有 DOM，读不了 CSS 令牌。所以改成**数据层只回 `colorIndex`**，由视图层用 `seriesColor()` 解析成字面值 —— 数据层保持纯净，色值的唯一来源仍是 tokens.css。

新配色（`--chart-1..4`）与品牌蓝同族：蓝 / 琥珀 / 绿 / 紫红。色相间隔够大，四条线并排分得清；饱和度压到接近语义色，不抢数据。

> ⚠️ 分类色**不携带语义**。一张图里"绿色那条"不代表它是好的 —— 表达好坏仍然用 `--ok` / `--warn` / `--danger`。

#### 数字排版

- **全局 `tabular-nums`**。界面里到处是需要纵向对齐的数值，比例数字宽度不一，永远对不齐。**"数字对不齐"是不精密最直接的来源**，而这一条只花了一行。
- **`--font-num` 改成无衬线体**。改造前是 Consolas 那类等宽字体 —— 宽度稳定，但一眼就是"开发者工具"，而这是医疗仪器界面。配合 tabular figures，无衬线体同样保证对齐，却没有那股代码味。
- **标签与值的层级差**。状态栏的值进一档加粗一档、标签退一档加字距 —— 两者一样大时读起来是一句话，拉开之后眼睛才会先抓到数字。

#### 顺带清掉的颜色不一致

- 状态栏呼吸光晕用的是 `rgb(103 194 58)`，即 **Element Plus 默认绿 `#67c23a`**，不是项目的 `--ok`
- 图表分类色是整套 EP 调色板（见上）

这类"差一点"最伤整体感：单看没问题，和项目自己的颜色摆一起就露馅。

⚠️ 查这个的时候**走错过一次方向**：以为 `token()` 读出来的字体栈带换行、导致 canvas 的 `ctx.font` 失效，还据此改了代码。实测发现 canvas 自己会归一化空白，图表从来没受影响。改动留着（内联 style 字符串确实受不了换行）但注释改成了实情 —— **错误的诊断留在注释里比没有注释更糟**。

#### 两个「静默出错」的图表 bug

这两个都是 2026-09-22 给分析页加结论时才发现的，共同点是**不报错、也不崩，
只是安静地输出一个错的东西**：

**① 「各动作达标对比」对靠墙静蹲比错了量。** 柱子取 `rom_deg`，而目标线取
`targetFor()` —— 后者对靠墙静蹲返回的是**保持角度**目标 55°。拿活动范围
（天然只有几度）去比，图上读作"完成 17%"，而那个患者其实做得完全正确。

同一页的概要用的是正确口径（`metricFor`），于是**页面自己和自己矛盾**。
这是同一个坑的**第四处**（另三处见「达标判定」一节），前三处都有断言钉着，
**这一处没有**，所以一直活到加结论的时候 —— 新结论说"靠墙静蹲达标"，
旁边的图说 17%。

**② 「关节活动度趋势」在康复的常态下是一张空图。** 一组配置凑在一起：

```
showSymbol: false      不画数据点标记
connectNulls: false    线段需要两个相邻非空点才画得出来
```

而这张图是"每个动作一条线"，患者每天练一个动作、四个动作轮着来 ——
于是每个动作的点之间都隔着 null，**既没有线段，也没有标记点**。

实测（1440 宽，量 canvas 上的彩色像素）：

```
每个动作隔几天练一次（常态）  →   0 个彩色像素
同一个动作连续几天练          →   2548 个彩色像素
```

这个 bug 一直没被发现，是因为**分析页当时对无数据的访客走空态、没有演示数据，
没有人看过这一页的图**。

改法是把 `showSymbol` 的默认值反过来 —— 理由是两种错法的代价不对等：

```
点太密   → 难看，但看得出有数据
点不显示 → 一张空图，而且不报错
```

密集波形（实时监测那四张）显式关掉。

### 界面图标：从 emoji 到 Lucide

原先界面上散着一批 emoji（🟢🟡🔴 / 📋🛡️⚠️💡 / ⓘ / → / ▾）。换成
`lucide-vue-next` 的矢量图标，理由有三条，**而且第二条是实质的**：

1. **跨平台一致。** emoji 由系统字体渲染，Windows / iOS / 各家安卓 ROM 上
   同一个 🟡 的大小、配色、边距都不一样，还会跟着系统版本变。
2. **形状本身携带信息。** 三档风险现在是 ✓ / △! / ✕。色盲用户分辨不出红绿，
   但分得出这三种形状 —— **原先三个都是"圆"，只能靠颜色**。
3. 不依赖 emoji 字体，精简系统上不会退化成方块。

代价实测：`dist` 总计 2104 → 2117 KB（未压缩，+13 KB / +0.6%）。

⚠️ 角标模式下图标**比文字大一号**（1.25em）。原先那里是**实心**的彩色圆，
换成描边图标后视觉重量轻了不少，而这个角标是卡片上**唯一的风险信号** ——
`RiskBadge` 的原注释写的"家属一眼就能认出来"是它的核心要求。

**顺手修的一处分层问题**：`SummaryCard.icon` 原先存的是 **emoji 字面量**，
而 `insight.ts` 是纯函数模块、能在 node 里跑，**碰不到 Vue** —— 把"显示什么"
和"长什么样"混在了一起，换个图标库要改到算法层来。现在存标识名
（`'clipboard'` 等），由视图映射成组件，而且标识名是联合类型，写错字编译期就报。

### 层次、材质与动效

#### 卡片微投影：推翻了本文件原先的一条原则

`tokens.css` 原本写着「**阴影只给浮层用**，静态面板靠描边区分层级」，
理由是"满屏阴影会让密集的数据区显得脏"。

那个顾虑是对的，但**结论下早了**。改造后整个应用是二十多张纯描边的白卡片
平铺在灰底上，所有东西都在同一个平面上 —— 界面看起来"贴"在背景上，缺一层。
这不是靠调颜色能解决的。

所以折中：**保留描边**（它负责清晰的边界），另加一层极轻的投影
（`--shadow-card`，两层叠加总透明度约 7%）负责"浮起 1px"。
比 Material 那种层级阴影淡一个量级 —— 作用是让卡片离开背景，不是营造深度。

20 多处卡片定义用脚本统一加的（只匹配"白底 + 1px 描边 + 圆角"的块，
避开 `.summary` 那种 grid），然后逐条审 diff。

#### 动效

| | 做法 |
|---|---|
| 路由切换 | `mode="out-in"`，出 80ms / 入 160ms（**2026-09-22 才真正补上，见下**） |
| 评分数字 | `composables/useCountUp.ts`。**首次直接落位、只在值变化时滚** —— 从 0 滚到 85 会读成"分数从 0 涨上来了" |
| 图表 | 入场 420ms、**更新 260ms**。更新必须快，否则每次改筛选条件都要等它"演"一遍 |

>
> `DefaultLayout.vue` 里一直有 `<Transition name="page" mode="out-in">`，注释也
> 一直写着"出 80ms / 入 160ms…总耗时 240ms"，但**全项目没有一行 `.page-*` 样式** ——
> `git log -S ".page-enter-active"` 为空，这套类名**从来没被写过**。没有 CSS 时
> Vue 判定"无过渡"，`mode="out-in"` 只让两页依次挂载，视觉上是瞬时切换。
>
> 也就是说：**注释描述了一个不存在的功能，README 又抄了一遍，两份文档互相背书。**
> 这正好是这个项目反复警告过的那类问题（`Dashboard.vue` 折叠区里留着同类记录：
> **写字面承诺之前先确认实现了没有**）。
>

> 不动 transform）。**实测验证过**：正常模式下 opacity 出现 8 个中间值、连续变化

对动画敏感，系统里关掉动效之后这里不能还在滚。

> 「可点卡片加 hover 抬升」没做 —— 首页那三张卡片**不是链接**，加 hover 会骗人。
> 没做的原因记在这里，免得以后有人以为是漏了。

### 模拟数据：让它更像真的

模拟器不是随机数发生器，但改造前有几处**一眼能看出是生成的**。四处改动：

#### ① 关节角度不再是余弦

改造前 `t % periodMs` 算相位、乘一条固定的余弦，结果是**每一轮都一模一样**：同样的周期、同样的幅度，画出来是一条完美的正弦。

真实患者做不到。现在每轮重抽参数，并且轨迹本身也换了：

```
改造前   对称余弦，两端只停留一瞬
改造后   较快地屈曲 → 最大屈曲位保持一下 → 较慢地回落
```

保持段是治疗师通常会要求的（"到顶停两秒"），**这个不对称也正是相位分析能看出东西的前提**。

幅度抖动**只往下**：疲劳让活动范围变小，物理上是单向的；而且上限必须卡住，否则"最大角度不超过 angleMax"那条断言会随机失败。

#### ② 温度改成指数趋近

改造前是**线性升温到目标后保持**。两个问题：形状不对（皮肤被加热是向热源温度**渐近**逼近，先快后慢），以及到达那一刻**斜率突变**，有个折角。

改成牛顿加热的形式之后，自检里能直接用一条断言区分两种实现：

```
前 20 秒升 5.09°C，中段 20 秒只升 1.16°C     ← 线性升温没有这个性质
```

#### ③ 应变与角度不再是线性关系

计划书里的 GF = 5.68 是「**0–50% 应变区间**」的平均灵敏度 —— 这句话本身就意味着各区间灵敏度不同。真实柔性传感器的导电网络在拉伸中会重排。

改成一条温和的幂曲线（低应变区变化慢、高应变区变化快）。单调，所以"应变与角度高度正相关"仍然成立。

> ⚠️ 这一改**踩出一个会进生产的 bug**：`x ** 1.35` 对负底数返回 NaN，而角度低于下限是**常态**（热敷场景的静止角约 4°、直腿抬高的 `angleMin` 是 2°，都低于映射用的 5°）。后果是应变分量整列 NaN，解耦图直接画不出来，而且**不报任何错**。
>
> 自检脚本抓到了它。顺手加了一条"所有采样值都是有限数"的断言 —— 这类 bug 只会以"图不显示"的形式暴露，没人会想到是数据里混了 NaN。

#### ④ 演示数据可复现

改造前演示数据每次刷新都变 —— **同一个页面刷新一次，分数从 81 变成 77**。排练时记住的数到台上就变了，这对要拿去比赛的演示是不可控的。

引入 `lib/rng.ts`（mulberry32 + 固定种子）。随机源是**逐个传进去的**，不是全局替换：

| | 随机源 | 为什么 |
|---|---|---|
| 演示数据 | 固定种子 | 每次刷新一致，可排练 |
| 实时监测 | `Math.random` | 那是"正在发生的信号"，每次都相同反而不真实 |

同一个模拟器代码，两种用法。

### 关于「专注模式」（做过，又撤了）

曾经在实时监测页放过一个深色「专注模式」开关。撤掉的原因值得记一笔：

**它只改颜色。** 全项目两处生效 —— 覆盖一组 CSS 变量、给四个图表传 `dark`。
没有任何功能上的区别。叫「专注模式」是名字夸大了，它实际是个配色方案。

而且连配色方案都不完整：访客提示条在暗色作用域之外，深色页面上顶着一条亮白条。

**为什么不再给它加功能，而是直接撤掉**：真正配得上"专注"的做法是收起一切非波形的东西
（提示条、控制面板、脚注）并把波形放大。那是另一个功能，不是这个开关的修补。
而眼下为了"换个颜色"维护两套完整配色，不值当。

撤掉的东西：`focusMode` 状态与开关、`.monitor--dark` 令牌作用域、
`chartTheme.ts` 里的暗色取值、`SignalChart` 的 `dark` 属性。

**顺带清掉一个真的问题**：状态栏那圈呼吸光晕原本写死成 `rgb(103 194 58)`，
那是 **Element Plus 的默认绿**，不是项目的 `--ok`。现在走 `--ok-glow` 令牌。

### 移动端导航

家属大概率用手机看，而顶部那行导航在手机上是要命的：**八个项挤在一行里横向
滚动，「关于」直接在屏幕外**，而没人会想到去横滑顶栏（它没有滚动条，也没有
任何提示）。顶栏还因此折成两行、占掉 90px 高度。

现在 ≤768px 时：

```
┌──────────────────────────────┐
│  概览  实时监测  康复评估  更多  │   ← 固定底栏，56px + 安全区
└──────────────────────────────┘
```

| 位置 | 项 | 为什么 |
|---|---|---|
| 底栏 | 概览 / 实时监测 / 康复评估 | 打开就想知道的；康复评估是这套系统的核心产出 |
| 抽屉 | 预警 / 数据分析 / 我的设备 / 监护管理 / 关于 | 不是"每次打开都要看"的 |

> ⚠️ 底栏第三格原先是「预警」，2026-09-22 与「康复评估」对调。**这次对调有代价**：
> 预警的未处理角标原先挂在底部，一眼就能看到有几条没处理；现在要先点「更多」
> 再打开抽屉才看得见。桌面端不受影响（顶栏有自己的预警角标）。

顶栏因此回到一行，高度 90px → 52px。

几个细节：

- **抽屉里每一项都带一句说明**。光看「监护管理」四个字，家属不知道那是干什么的。
- **当前页在抽屉里时，「更多」要亮**。否则用户在「康复评估」页上，底部四个 tab 一个都不亮，会以为自己不在导航体系里。
- **主内容区要留 `padding-bottom`**。固定定位的元素不参与文档流，少了这一条页面最后一行会被永久挡住，滚到底也翻不上来。已用「滚到底后最后元素底边 ≤ tab 条顶边」验证。
- **iPhone 的 Home 指示条**：底栏和抽屉都要 `env(safe-area-inset-bottom)`。

⚠️ `el-drawer` 的 `class` 透传到它**内部渲染出来的 div** 上，不是组件根元素。Vue 只给子组件的**根元素**附加父组件的 `data-v` 属性，所以 `.more-drawer` 上没有 scope 属性，**`:deep()` 也选不中** —— 规则会静默失效，抽屉底部保留 Element Plus 默认的固定 20px。要改它只能用不加 `scoped` 的 style 块（`MobileTabBar.vue` 里有一个，选择器带 `.more-drawer` 前缀所以不会外泄）。

### 关于「家属模式 / 专业模式」

**做过，又撤掉了。**

曾经在顶栏放过一个开关：家属模式下正文 18px、控件 44px，波形 / RMS / 相位环路
等技术内容默认折叠；专业模式回到 13px 密集布局并展开全部内容。

撤掉的原因是定位变了 —— 这是一个**传感器**竞赛项目，把波形藏起来会低估技术含量。
现在统一是密集布局，技术内容全部直接显示。

**保留下来的**是与模式无关的那部分：结论层（恢复评分 / 红黄绿 / 建议）、
无历史时的演示数据、首页的健康摘要布局。
**撤掉的**是模式切换本身、双轨字号、以及各页的折叠区。

⚠️ 连带放弃了之前按 WCAG 2.1 AA 定的三条：正文 ≥18px、触控目标 ≥44×44px、
次要文字对比度 ≥4.5:1。现在是 **正文 13px / 控件 32px / `--ink-400` 对白底 3.6:1**。

如果将来要投医疗场景、或做适老化版本、或评审要求无障碍合规，这几条得重新捡起来。
实现方式见历史提交 `c43882f`（首页 + 双轨字号）与 `6291d60`（三页的折叠与结论卡），
核心手法是在 `<html>` 上挂 `data-view`、由 `tokens.css` 整组覆盖令牌 ——
不需要给任何组件写第二份样式。

### 演示数据：`src/lib/demoData.ts`

摘要页的价值建立在**历史**上，而第一次打开链接的人（评审、家属、队友）一定没有历史，只会看到一个空页面。所以没有记录时用一组演示数据兜底。

**它只在内存里算，绝不写数据库**，而且**明确标注**「演示数据」—— 项目的一条底线是不把模拟数据说成实测数据，演示数据同样适用。数据本身走的是与真实评估完全相同的链路（`generateSession`），页面上的每个数字都是这套系统的算法产出的，不是手编的。

### 监护关系（家属远程查看）

产品需求是"把康复数据同步到子女手机"，数据库层从阶段 2 起就按这个设计（`care_links` 表 + `is_caregiver_of` 等策略）。前端在阶段 9 补齐。

**建立关系的流程**：

1. 患者在自己的「监护管理」页看到一串 **6 位邀请码**
2. 把码发给家人（微信即可）—— 码去掉了 I/L/O/0/1 这些形近字符，方便念和手输
3. 家属在「监护管理」页输入码发起申请，状态为**待确认**
4. 患者在页面上确认后关系才生效

**为什么用邀请码而不是按邮箱查找**：`profiles` 表里没有 email（邮箱在 `auth.users`，不对外暴露）。就算加一列，RLS 也只允许读已建立关系的对方资料 —— 家属在建立关系**之前**恰恰看不到患者。而按邮箱查人会引入**邮箱枚举漏洞**：任何登录用户都能拿它试探哪些邮箱注册过。Supabase 的注册接口刻意对已存在的邮箱返回假用户就是为了堵这个口，不该在别处再开一个。

**权限边界**（都已在真实环境端到端验证）：

| 行为 | 是否允许 |
|---|---|
| 家属发起申请 | ✅ 但只能是 `pending` |
| 家属自己批准 | ❌ 触发器拦截，只有患者本人能改成 `active` |
| 家属读患者的训练/设备/预警 | ✅ 关系生效后 |
| 家属改患者资料 | ❌ RLS 静默过滤，值不变 |
| 家属改关系类型 | ❌ 列级授权只开放 `status` |
| 患者撤销后 | ✅ 立即失效 |
| 无关第三方 | ❌ 全程不可见 |

**家属查看多个对象时**：数据页面按"当前查看对象"过滤，顶部有常驻提示条说明正在看谁的数据。没有这条提示的话，两张长得一样的表很容易被当成自己的看。

## 运维：Supabase 保活

Supabase 免费版项目连续 **7 天无活动会被自动暂停**，恢复需人工操作。`.github/workflows/keep-alive.yml` 每天调用一次数据库里的 `ping_keepalive()` 维持活跃。

首次使用需在仓库中添加两个 secret（Settings → Secrets and variables → Actions）：

| Secret | 值 |
|---|---|
| `SUPABASE_URL` | `https://<项目ref>.supabase.co` |
| `SUPABASE_ANON_KEY` | publishable key 或 anon key |

加完在 Actions 页面手动跑一次验证。两个 secret 缺任意一个，工作流会明确报错而不是静默失败。

⚠️ **GitHub 会在仓库连续 60 天无活动后停用定时工作流。** 开发期间有提交所以不受影响，但项目如果长期搁置需要留意——届时去 Actions 页面手动重新启用即可。
